# 密码加密

连接里保存的数据库密码、SSH 密码和 SSH 通行短语怎么加密，密钥放在哪里，以及偏好设置里的“主密码”做什么。行为契约仍以 [11-connection.md](11-connection.md) 第 7 节为准，本文解释那一节在各系统上的实际表现。

## 1. 存的是什么

`connections.json` 里的主机、端口、用户名、是否保存密码都是明文。加密的只有三个字段，每个字段单独一个信封：

| 字段 | JSON 位置 | 关联数据 |
| --- | --- | --- |
| 数据库密码 | `general.password` | `{连接 ID}/general.password` |
| SSH 密码 | `ssh.password` | `{连接 ID}/ssh.password` |
| SSH 通行短语 | `ssh.passphrase` | `{连接 ID}/ssh.passphrase` |

信封是 `{ "nonce": "…", "ct": "…" }`，两段都是标准 Base64。算法是 XChaCha20-Poly1305：32 字节密钥，每条密文一个随机 24 字节 nonce。关联数据绑在这一条密文上，所以把一个字段的密文换到另一个字段或另一个连接上，解不开。

“保存密码”没勾选时，对应字段写成空，文件里不留密文。下次打开这个连接时弹出询问密码，问的是数据库或 SSH 的密码，和下面的密钥不是一回事。

连接的每一份配置文件（`profiles`）里的秘密字段用同一套规则。设置、修改、清除主密码，以及复制连接时，会把非当前配置文件换到当前槽位上再加密，避免漏掉。

文件位置：

| 系统 | 路径 |
| --- | --- |
| macOS | `~/Library/Application Support/navidog/connections.json` |
| Windows | `%APPDATA%\navidog\connections.json` |
| Linux | `$XDG_CONFIG_HOME/navidog/connections.json`，未设置时是 `~/.config/navidog/connections.json` |

`NAVIDOG_HOME` 可以改掉这个目录。写入先落到临时文件，再原子替换。

## 2. 两种密钥

所有密文共用一把 32 字节密钥。密钥从哪来，由文件顶层的 `crypto` 决定。同一时间只有一种模式。

### 本机密钥（默认）

`{ "kind": "machine" }`。第一次需要加解密时生成 32 字节随机数，Base64 之后放进系统凭据存储。数据库密码不进钥匙串，钥匙串里只有这把密钥。

读取发生在 `ConnectionStore::key`。读到之后缓存在这次运行的内存里，同一个进程再打开别的连接不再去碰系统凭据存储。退出进程后缓存消失，下次启动再读一次。

service 是 `ci.nn.navidog`，account 是 `config-key`。这两个名字不能改，否则对不上已经写进去的密钥。

### 主密码

用户在偏好设置里设了一句自己记得住的密码。密码本身不写入文件，也不进钥匙串。文件里只留：

```json
{
  "kind": "master",
  "salt": "…",
  "m_kib": 19456,
  "t": 2,
  "p": 1,
  "check": { "nonce": "…", "ct": "…" }
}
```

`salt` 是 16 字节随机数的 Base64。密钥用 Argon2id（版本 0x13）从主密码和这份盐派生，参数是 OWASP 的建议：19 MiB 内存、2 次迭代、1 路并行，输出 32 字节。`check` 是用这把密钥加密固定串 `navidog-master-check`（关联数据是 `check`）的结果，用来判断输入的主密码对不对。密码错时派生出另一把密钥，`check` 解不开。

盐在文件里，所以同一份 `connections.json` 配上同一句主密码，在另一台机器上能派生出同一把密钥。本机密钥做不到这一点：密钥留在原来那台机器的凭据存储里，文件拷走之后解不开。

## 3. 各系统上的本机密钥

`keyring` 3 按编译 feature 选择系统存储。现在只打开了 `apple-native`。某个系统没有对应 feature 时，`keyring` 用它自带的 mock：条目不跨调用保留，更不跨进程保留。

| 系统 | 现在实际用的存储 | 表现 |
| --- | --- | --- |
| macOS | 登录钥匙串。钥匙串访问里能看到名称 `ci.nn.navidog`、账户 `config-key` 的通用密码 | 见下一节 |
| Windows | mock，没有编入 `windows-native` | 密钥只在这一次运行的内存缓存里。退出后再启动会生成一把新密钥，原先的密文解不开，那些连接被当成没保存密码，数据不删 |
| Linux、FreeBSD、OpenBSD | mock，没有编入 secret-service 或 keyutils | 与 Windows 相同 |

主密码模式不读系统凭据存储，所以在 Windows 和 Linux 上也能跨重启解密。在这两个系统上，如果需要已保存的密码在重启后还在，就要设主密码。

以后若要让本机密钥跨重启可用，再打开对应 feature：Windows 是 `windows-native`（凭据管理器里的通用凭据，同一用户读取通常不再弹框）；Linux 是同步的 secret-service（GNOME 钥匙环、KWallet 等，会话未解锁时由桌面环境询问一次）。那是以后的事，现在没有编进去。

## 4. macOS 上的钥匙串授权

弹出的不是“请输入数据库密码”。系统问的是：这个程序能否读取钥匙串里 `ci.nn.navidog` 的机密。允许之后，程序拿到的是加密密钥，再用它解开 `connections.json` 里的字段。

对话框会反复出现，是因为调试构建没有稳定的代码签名。`cargo run` 每次编译，二进制的签名都变。钥匙串把“始终允许”记在旧签名上，下一个二进制对不上，于是再问。正式签名并且签名保持不变之后（发布阶段，M15），“始终允许”才能留住，之后启动不再问。

一次读取可能连续弹出两个授权框。`keyring` 在 macOS 上调用 `SecKeychainFindGenericPassword` 时，同时要了密码和钥匙串项；系统对尚未信任的程序会分开询问。曾经改成只取密码、不取钥匙串项，在这台机器上第二个框仍然出现，所以读取改回 `keyring`，不再自己调 Security 框架。从程序这边消掉第二个框，目前没有可靠的办法。

同一次运行里授权过一次之后，密钥留在内存里。再打开另一个保存了密码的连接，不会再读钥匙串。

钥匙串不可用，或条目丢了、被拒绝，秘密字段解不开。程序记下失败，这个连接按“没保存密码”处理，请用户当场输入。`connections.json` 里的密文保留，不删除。

## 5. 设置里的主密码

位置：偏好设置 → 高级 → 主密码。

旁边的说明有两句。没设主密码时是“保存的密码使用钥匙串中的密钥加密”。设了之后是“保存的密码受主密码保护”。

| 操作 | 界面 | 做了什么 |
| --- | --- | --- |
| 设置主密码 | “设置主密码…”，新密码输入两遍 | 用新盐派一把密钥，把每个连接、每份配置文件里的秘密字段用旧密钥解开，再用新密钥加密，然后把 `crypto` 写成 `master` 并原子写回。这次运行里密钥留在内存，不用立刻再输一遍 |
| 修改主密码 | “修改主密码…”，同样只输入新密码两遍 | 和设置相同：再换一把盐和密钥，全部重加密。不要求在对话框里输入旧主密码 |
| 清除主密码 | “清除主密码” | 切回本机密钥，用钥匙串里的那把密钥把全部秘密字段重加密。macOS 上如果这次运行还没读过钥匙串，这里会触发一次钥匙串授权 |

设置和修改都要求这次运行已经拿得到当前密钥。本机密钥模式下，点设置会先读钥匙串。主密码模式下，如果这次运行还没解锁，设置、修改、清除都会失败，提示需要先解锁。解锁的入口是打开一个保存了密码的连接，不是偏好设置本身。

重加密要么全部完成，要么文件不动。只要有一个字段用当前密钥解不开（例如另一把已经找不回的密钥写进来的密文），设置、修改、清除都会失败并提示“有保存的密码无法用当前的密钥解开”，已有的密文一个都不改。在对话框里按回车和点“确定”一样，只执行一次。

两遍新密码不一致，或有一遍是空的，对话框留下“两次输入的密码不一致”，文件不动。

## 6. 启动后的解锁

设了主密码时，文件里没有密钥，程序也不能从主密码以外的材料把它算出来。这次运行第一次要解开某个已保存的秘密时，弹出“解锁 Navidog”，要求输入主密码。

输对之后，派生出的密钥缓存在内存里，直到退出。这次运行里再打开别的连接不再问。

输错计一次。连续三次失败后，这次运行不再弹出解锁框。还没解开的连接按“没保存密码”处理，可以在询问密码对话框里手动输入数据库密码。已经写在文件里的密文不动。下次启动重新从零次失败开始。

主密码忘了就解不开这些密文。没有找回途径。清除主密码也做不到，因为清除同样要先用旧密钥解开再重加密。
