## 3. 问题说明

### CR-01 重连丢掉已切换的目标库（严重）

位置：`crates/navidog-db/src/mysql.rs:200-215`、`crates/navidog-db/src/postgres.rs:468-478`（`execute` 里 `lost` → `reconnect` → 重试）；配合 `crates/navidog-query/src/run.rs:326-340`。

机制：查询编辑器切目标时发 `USE <库>` / `SET search_path TO <模式>`，并把结果记进 `live.used`（`run.rs:338`）。`reconnect` 只按连接参数重建会话（MySQL 用 `self.opts`，PostgreSQL 用 `self.params`），重放的只有那条语句本身；`live.used` 不重置，所以编辑器认为目标已经切好、不会再发一次。触发条件是服务器端断开：`wait_timeout` 到期、服务器重启、管理员 `KILL`、网络抖动后 `ping` 或下一条 `execute` 走到重连。此后该选项卡里未限定库名的语句（`SELECT` / `INSERT` / `UPDATE`）会落到连接的默认库，而不是用户以为的那个库。

修法：`reconnect` 成功后重放最近一次的 `USE` / `search_path`（在 `Session` 上记一个 `session_target: Option<String>`，由 `execute` 在识别到 `USE`/`SET search_path` 时写入），或者把「断线重连」作为事件暴露给 `run.rs`，让它把 `live.used` 置 `None` 并重下目标。前者改动小，后者语义更干净。需要补一个测试：注入一次断线，断言重连后目标仍然生效。

### CR-02 tag 发布停在 draft（重要）

位置：`.github/workflows/publish.yml:69-81`（`gh release create "$tag" --draft`）、`435-467`（`checksums` 作业）、`.github/workflows/upload_asset.sh:34`（回退时也建 draft）。

机制：tag 构建只把资源上传到这个 draft release，工作流里没有任何 `gh release edit --draft=false` 或等价步骤（`softprops/action-gh-release` 那三步都带 `if: github.ref == 'refs/heads/main'`，只服务 nightly）。客户端稳定渠道读的是 `crates/navidog/src/update.rs:29` 的 `.../releases/latest/download/latest.json`，而 `/releases/latest` 不含 draft 与 prerelease，因此会 404 并退化到 `fetch_from_api`（同样不含 draft），最终表现为「检查更新」永远说没有新版本。00-overview §工程 3 与 progress.md §4 都没写「draft 由人工发布」这一步。

修法：在 `checksums` 之后加一步 `gh release edit "$TAG" --draft=false`（建议在 `SHA256SUMS` / `latest.json` 都上传成功之后），或者在 00-overview 与 progress.md §4 明确登记「draft 由人工审阅后发布」。二选一，但必须落地。

### CR-03 nightly 跳过 SHA-256 校验（重要）

位置：`crates/navidog/src/update.rs:181`（`assets_from_api` 造出 `sha256: String::new()`）、`crates/navidog/src/update.rs:391`（`if !asset.sha256.is_empty() && …`）；`.github/workflows/publish.yml:191,437`（checksum 步骤都带 `if: startsWith(github.ref, 'refs/tags/')`）。

机制：nightly 渠道走 `fetch_from_release_list` → `assets_from_api`，`sha256` 为空串，`download_verified` 于是整段跳过校验；预发布标签在拉不到该 tag 的 `latest.json` 时同样回退到这条路径。而 `docs/design/00-overview.md` 决策 14、`01-feature-inventory.md` 的 F-REL-003、以及 progress.md §3 新写的 F-REL-003 行都写「下载后按 SHA-256 校验」，§4 没有登记这个偏差。

修法：三条路选一条——nightly 也生成并上传 `SHA256SUMS` / `latest.json`；或读 GitHub API 的 asset `digest`（`sha256:…`）填进 `ManifestAsset`；或把偏差写进 progress.md §4 并把 F-REL-003 记回「部分」。校验本身已经有 `hex_encode` 与比较逻辑，缺的只是 nightly 的摘要来源。

### CR-04 就地替换 `.app` 的回滚可能静默失败（重要）

位置：`crates/navidog/src/update.rs:466-483`。

机制：`replace_bundle` 先把旧 `.app` `rename` 到临时目录，再用 `ditto` 把 DMG 里的 `.app` 拷到原位置；拷失败时靠 `let _ = std::fs::rename(&aside, app)` 回滚。`ditto` 半途失败通常已经在目标位置建出部分 `.app`，`rename` 到非空目录会失败，而错误被 `let _ =` 丢掉，用户的应用就停在半残状态；`install_macos` 接着还会 `open(dmg)`，把安装包也弹出来。此外旧包留在 `temp_dir()/navidog-old-<pid>.app` 不清理。

修法：回滚前先 `remove_dir_all(app)`（或把新包拷到 `<app>.new`，校验成功后再原子换名），回滚失败要 `tracing::error!` 并返回明确错误；成功路径清理 `aside` 与下载目录。

### CR-05 「立即重新启动」可能不会启动新版本（重要，需实测）

位置：`crates/navidog/src/update.rs:495-501`（`relaunch`）、`735-741`（对话框里 `relaunch(); cx.quit();`）。

机制：`relaunch` 用 `open <app>`，此刻当前进程仍在运行，且 `replace_bundle` 已经把同一路径下的 bundle 换成了新版本。LaunchServices 按 bundle id 判断「已经在跑」，多半只是激活现存实例而不再拉起新进程；紧接着 `cx.quit()` 退出，结果是应用被关掉、新版本没起来。

修法：需要在一台装好的 `.app` 上点一次「立即重新启动」确认（看是否出现新进程、版本号是否变）。如果确认有问题，改成 `open -n <app>`，或起一个 detached 脚本等当前 pid 退出后再 `open`。这条要实测，所以记「待确认」。

### CR-06 Linux 本机密钥文件不是原子写（重要）

位置：`crates/navidog-core/src/crypto.rs:222-244`。

机制：`create_new` 先建出 0 字节文件，再 `write_all` 写入 44 字节 base64，中间没有 `sync_all`。进程在这两步之间被杀掉、或写时磁盘满 / 权限异常，都会留下 0 字节或半截文件；下一次启动 `read_to_string` 成功但 `decode_key("")` 得到 `CryptoError::Format`，而 `read_or_create_key_file` 只报错、不重建。之后所有已保存的密码都解不开，按 12-secrets 的重加密流程还会把它们清掉，属不可恢复。macOS 与 Windows 走钥匙串不受影响，所以受影响的只有 Linux（默认路径，没有 keyring）。

修法：同目录写临时文件（同样 `0600`）+ `sync_all` + `rename` 覆盖；不能直接用 `paths::write_atomic`，它是按默认权限建的。另外可以让 `decode_key` 失败视为「没有密钥」并重建（要权衡：那会让旧密文永远读不出，只在前一种修法无法保证时再考虑）。

### CR-07 工作流按 `main` 触发，默认分支是 `master`（重要，待确认）

位置：`.github/workflows/publish.yml:16,50,63,211,316,422`、`integration.yml:5`、`smoke.yml:5`、`audit.yml:5`；对照 `docs/design/00-overview.md:81`「通过 PR 合并到 `master`」。

机制：本地 `origin/HEAD -> origin/master`，规格也写 `master`；但 nightly 的打包、上传与 `NAVIDOG_BUILD_CHANNEL=nightly` 判定、以及 smoke / integration / audit 的 `push: branches: ["main"]` 都以 `main` 为准。如果主线确实是 `master`，那么：推送不会触发这三个工作流；每天定时的 nightly 构建会把三平台都编一遍，然后因为 `if: github.ref == 'refs/heads/main'` 全部跳过上传，白跑一轮。

修法：先确认主线分支名（GitHub 仓库设置里的默认分支）。定为 `master` 就把工作流里的 `main` 全改掉；定为 `main` 就改 00-overview §工程 4 与 AGENTS.md 里的说法。`rust-toolchain.toml` 那类一致性检查可以照抄一份分支名的检查。
